# RATES-BRIDGE-CONTRACT

Договор о передаче курсов **касса (CoinPlata) → CoinPoint**. Версия черновика:
2026-09-02. Сторона кассы описана по факту кода; сторона CoinPoint — по
`coinpoint/docs/RATES_MAP.md` и коду ветки `main`.

> **Статус:** черновик. Разделы, помеченные ⛔, требуют решения владельца или
> подтверждения со стороны CoinPoint и НЕ реализуются до ответа.

---

## 1. Зачем

Сегодня курсы живут в трёх независимых системах, и между кассой и CoinPoint
синхронизации каталога курсов **нет вообще** (`RATES_MAP.md` §4). Каждая
заявка несёт свой курс, но справочник не общий: касса, сайт и бот могут
показывать разные цифры одновременно.

Цель: **касса — единственный редактор курсов**, CoinPoint и все его витрины
(сайт, `/rates`, мини-апп, клиентский бот, мобильное приложение, агрегаторы) —
только потребители.

## 2. Что публикует касса

Публикация уже реализована: RPC `publish_rates` пишет версию в
`public.rate_publications` (append-only), `get_published_rates` отдаёт
последнюю. v.1 создана 01.09.2026, 42 цены.

```jsonc
{
  "version": 1,                       // монотонная, +1 на публикацию
  "published_at": "2026-09-01T19:14:36Z",
  "prices": [                         // плоский прайс, посчитанный rateEngine
    { "block": "usdt", "scope": "ANT", "from": "USDT", "to": "TRY", "rate": 47.40 },
    { "block": "qr",   "scope": null,  "from": "RUB",  "to": "USDT", "rate": 93.45 },
    { "block": "nerez","scope": "TOD-TOM", "from": "USDT", "to": "RUB", "rate": 87.13 }
  ],
  "inputs": { "values": {}, "locks": {} },   // сырой ввод, для наследования
  "source_meta": { "editor": "v2", "sources": { "tolunay": { "fetched_at": "…" } } }
}
```

### 2.1. Ключ строки и его смысл

Строка адресуется четвёркой `block · scope · from · to`.

**`scope` — это ИЗМЕРЕНИЕ БЛОКА, а не всегда город.** Это главный подводный
камень контракта:

| Блок | Что в `scope` | Разворачивать по офисам? |
|---|---|---|
| `cash` (Нал) | `null` — курс общий | нет, применяется ко всем турецким офисам |
| `usdt` | город: `ANT` / `IST` / `MSK` / `SPB` | да, город → офисы города |
| `qr` | город (`ANT`/`IST`) у подсчёта, `null` у якоря | да, кроме якоря |
| `perestanovka` | **маршрут офисов** `<office_id>→<office_id>` | нет, это уже офисы |
| `nerez` | **расчётный базис** `TOD-TOD` / `TOD-TOM` / `TOM-TOM` | **нет — базисы не города** |

Разворот НЕРЕЗ по офисам Антальи — ошибка, а не оптимизация. Правило записано
в комментарии к колонке `rate_rows.scope` в самой базе.

### 2.2. Ориентация — ОДНО ПРАВИЛО

Значение строки `from → to` — это **всегда «сколько единиц `to` за 1 единицу
`from`»**. Одно правило на модель, публикацию и всех потребителей. Принимающая
сторона **ничего не инвертирует сама**.

```
USDT → TRY = 47.40      лир за 1 USDT
TRY  → USDT = 0.020683  USDT за 1 лиру      (обратная сторона, свой спред)
USDT → EUR = 0.85251    евро за 1 USDT
RUB  → USDT = 0.010701  USDT за 1 рубль
```

**Почему это записано отдельным разделом.** До 02.09 в модели жили две
конвенции: блоки USDT и Нал хранили числа так, как их пишет Paramon («слабая
за 1 сильную»), а Перестановки и QR — так, как считаем мы. Внутри кассы
расхождение было незаметно, а аудит нашёл его на живой публикации: `RUB→TRY`
уходил в двух разных единицах, и QR к евро разошёлся с рынком на 20,8%.

**Кассир при этом видит числа сообщения.** Перевод «документ ↔ канон» делает
`src/lib/rateOrientation.js` по силе валют (правило перенесено из работающего
парсера coinpoint). Хранение и показ разделены сознательно: сверка утреннего
сообщения с экраном обязана оставаться буквальной.

### 2.3. Чего в публикации НЕТ

- **Комиссии за объём** — см. §5. Курс чистый.
- Резервов (`amount` в XML агрегаторов) — касса их не считает, см. ⛔ §7.1.
- Минимумов и максимумов сделки — ⛔ §7.2.

## 3. Транспорт

Направление касса → CoinPoint, тем же способом, что уже работает для заявок
(`api/cashdesk/status.js`): секрет живёт на сервере, во фронт не попадает.

```
POST {COINPOINT_API_URL}/api/internal/cashdesk/rates
     x-cashdesk-secret: {CASHDESK_API_SECRET}
     content-type: application/json

     { version, published_at, prices, source_meta }
```

Env уже провижены в проде кассы: `COINPOINT_API_URL`, `CASHDESK_API_SECRET`,
`CRON_SECRET`. Новых секретов не требуется.

⛔ **Путь эндпоинта требует подтверждения со стороны CoinPoint** — по аналогии
с `/api/internal/cashdesk/orders`, но фактического роута для курсов там нет.

### 3.1. Идемпотентность

Ключ — **номер версии**. Повторная доставка той же версии обязана быть
безопасной: CoinPoint сравнивает `version` с уже принятой и отвечает
`{ ok: true, applied: false }`, ничего не меняя. Это делает ретраи и ручное
«переотправить» безвредными по построению.

Версии монотонны и append-only: удалений в `rate_publications` нет (RLS без
delete). Откат — это публикация новой версии со старыми значениями, а не
удаление.

### 3.2. Ретраи и статус доставки

- Отправка — сразу после успешной публикации, синхронно с действием кассира.
- Неуспех (сеть, 5xx, таймаут) → повтор с задержкой 1с / 5с / 30с, три
  попытки. Дальше — состояние «не доставлено» и ручная кнопка.
- 4xx **не ретраится**: это ошибка контракта, её чинит человек, а не повтор.
- Кассир видит статус на Экране 3 и может нажать «Переотправить» — та же
  версия, тот же ключ идемпотентности.

⛔ **Где хранить статус** — решение: колонки в `rate_publications`
(`delivered_at`, `delivery_attempts`, `delivery_error`) либо отдельная таблица
`rate_deliveries` (строка на канал). Вторая нужна, если каналов больше одного
и они доставляются раздельно.

## 4. Как CoinPoint раскладывает полученное

Касса **не знает** про внутренние справочники CoinPoint и не должна знать.
Маппинг живёт на стороне получателя:

| Из публикации | В CoinPoint |
|---|---|
| `block=usdt, scope=ANT, USDT→TRY` | `coinpoint.rates` (direction USDT→TRY, city ANT) |
| `block=cash, scope=null, USD→TRY` | `coinpoint.rates`, город — все турецкие |
| `block=qr, scope=ANT, RUB→TRY` | секция СБП страницы `/rates` |
| `block=nerez, scope=TOD-TOM` | секция НЕРЕЗ (`paramon_rates`-эквивалент) |
| `block=perestanovka, scope=A→B` | перестановки между офисами |

**Наценка в курсе уже учтена** (`RATES_MAP.md` §2: «сайт спреды не
добавляет»). Принимающая сторона курс не модифицирует.

### 4.1. Потребители, которые переключаются автоматически

Все витрины CoinPoint читают **свои же API**, а не базу напрямую — кроме двух
мест:

| Витрина | Источник | Переключится сама? |
|---|---|---|
| Сайт `/rates` | `/api/rates-all` | да |
| Домашний калькулятор | `/api/rates?city=` | да |
| Мини-апп | `/api/rates` | да |
| Клиентский бот | `coinpoint.rates` + фолбэк `/api/rates` | да |
| Мобильное приложение | те же API | да |
| Агрегаторы | `/rates.xml` | да |
| ⚠️ Сабмит заявки из аккаунта | **читает `rates` напрямую из БД** | да, если пишем в ту же таблицу |
| ⚠️ Админ-форма заявки | `/api/rates?city=` | да |

Вывод: если принимающая сторона кладёт публикацию **в `coinpoint.rates`**,
все шесть витрин получают её без единой правки. Это и есть самый дешёвый
путь — менять источник, не трогая потребителей.

## 5. Комиссии за объём

**Комиссия НЕ входит в курс и передаётся отдельно.** Три причины:

1. Комиссия зависит от **суммы сделки**, курс — нет. Смешав их, мы получили бы
   курс, верный только для одной суммы.
2. BestChange и Exnode требуют комиссию **отдельными тегами** `<fromfee>` /
   `<tofee>`. Зашитая в курс комиссия сделала бы выгрузку неверной.
3. Правила уже живут на стороне CoinPoint (`bot_settings.data.city_commissions`,
   применяются в `applyCityCommission`) и редактируются в админке.

Текущие правила (зеркало дефолтов `web/app/utils/city-commission.ts`):

| Город | Порог | Комиссия |
|---|---|---|
| ANT | сделка < $2 000 | $10 |
| IST | сделка < $10 000 | $20 |

⛔ **Решение владельца:** остаются ли комиссии за объём на стороне CoinPoint
или переезжают в кассу вместе с курсами. Аргумент за переезд: «касса —
единственный редактор» должно означать и комиссии тоже, иначе цена для клиента
всё ещё собирается в двух местах. Аргумент против: правила уже работают,
и их перенос — отдельный риск поверх моста.

## 6. Выгрузка для BestChange

На стороне CoinPoint уже есть `web/server/utils/rates-xml.ts` — билдер
**формата семейства BestChange**, сделанный под Exnode, с тегами `from`, `to`,
`in`, `out`, `amount`, `fromfee`, `tofee`, `minamount`, `maxamount`, `city`,
`param`. Отдаётся как `GET /rates.xml`, `Cache-Control: no-store`.

Что это значит для нас: **отдельную выгрузку под BestChange писать не нужно** —
нужен второй роут с их справочником кодов и их набором обязательных полей.

Требования BestChange, которые надо соблюсти на нашей стороне:

- Курс всегда актуальный: файл отдаётся live, без кэша (уже так).
- `<in>`/`<out>` — «1» на дорогой стороне (уже реализовано в `normalizeInOut`).
- Комиссия — только `<fromfee>`/`<tofee>`, не в курсе (см. §5).
- Резерв `<amount>` — обязателен ⛔ §7.1.
- `<city>` — для наличных направлений, коды из справочника агрегатора.
- Коды валют — **их справочник**, не наш: маппинг живёт рядом с
  `EXNODE_CODES`, отдельной таблицей для BestChange.

⛔ Нужен доступ к личному кабинету BestChange: их список кодов валют и точный
набор обязательных полей меняются, и брать их «по памяти» нельзя.

## 7. Открытые вопросы

### 7.1. Резервы ⛔
Агрегаторы требуют `<amount>` — сколько валюты доступно. Касса знает **остатки
по счетам** (движения), но остаток кассы ≠ резерв, который мы готовы показать
рынку. Нужно правило: показывать фактический остаток, фиксированное число или
процент от остатка.

### 7.2. Минимумы и максимумы сделки ⛔
`<minamount>` / `<maxamount>` в модели курсов кассы отсутствуют. Хранить их
per-направление в `rate_rows` или брать из настроек CoinPoint?

### 7.3. Что делать при протухшей публикации ⛔
Если касса не публиковала сутки, витрины показывают вчерашние курсы. Нужен
порог, после которого потребитель обязан либо скрыть направление, либо
показать предупреждение. Для агрегаторов «старый курс» опаснее «нет курса»:
клиент придёт по цене, которой нет.

### 7.4. Кто главный на переходный период ⛔
Пока мост не включён, боевые курсы CoinPoint правятся менеджерским ботом и
админкой. В момент включения источник меняется — редактирование на стороне
CoinPoint должно быть заглушено, иначе две правды вернутся.
