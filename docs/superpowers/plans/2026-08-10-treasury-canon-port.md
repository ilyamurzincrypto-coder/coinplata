# Казначейство CoinPlata — порт финансового канона CP PAY под обменный контур

План на утверждение. Код — только после «да». Эталон: `ilyamurzincrypto-coder/coincash` (CP PAY),
плюс уже существующий ledger-контур кассы (Этап 1 ledger-activation закрыт).

> Главный вывод аудита: **ядро канона в кассе уже стоит на ~60–70%** (двойная запись,
> Σ=0-триггер, идемпотентность, append-only, план счетов 1xxx–5xxx, treasury-UI с Активы/
> Пассивы/Капитал/Журнал/Проводки/Оборотка). Проект = **достройка** (позиции+формы, 5 операций
> обмена, инвентаризация-старт, выравнивание UI под канон), а не перенос с нуля.

## (а) Аудит текущего репо кассы

**Стек.** Vite 5 + React 18 + Tailwind 3, без роутера (переключение страниц `useState` в App.jsx),
без стейт-менеджера (Context-провайдеры). Бэкенд — Supabase (Postgres, project `ygtphuxzazxdtyouxxir`).
Деньги — `utils/money.js` (минорные единицы, integer-minor арифметика). npm, деплой Vercel.

**Что из учёта УЖЕ есть (переиспользуем, не переписываем):**
- `ledger`-схема: `accounts`(code,name,type,subtype,currency_code,custody_type,office_id,
  parent_account_id,client_dim_required,partner_dim_required,allow_negative), `transactions`
  (idempotency_key, source_kind, reverses_transaction_id, status posted|reversed|released, metadata),
  `journal_entries`(direction dr/cr, amount, currency_code, client_id/partner_id/deal_id), `balances`,
  `idempotency_keys`(key, request_hash).
- **Инварианты триггерами** (это и есть канон): `tx_check_balance` — **Σ Dr=Cr per currency_code**
  на транзакцию, CONSTRAINT TRIGGER DEFERRABLE; `tx_check_completeness` — posted ≥2 проводок;
  `je_currency_match`; `je_dim_required`; `update_balance_on_entry`. UPDATE/DELETE на app-ролях
  отозваны → **append-only**, правки только через reversal-каскад.
- **Идемпотентность**: `idempotency_keys` + `request_hash`, ключ выводится из хэша (клиент —
  `newLedger.js`). *Но нейминг ключа не канонический* (см. конфликты).
- **RPC**: `create_deal_v2`, `create_transfer`, `create_adjustment`, `create_manual_entry`
  (N-плечевая проводка, owner/accountant-gated), `update_deal_v2` (reverse+recreate), `void_deal`,
  `complete_deal_leg`.
- **План счетов** (262 счёта): asset 1xxx (cash 111x-1143, crypto 13xx, inter_office 14xx,
  clearing 16xx/19xx), liability 2xxx (customer_liab 21xx, partner_liab 22xx, unearned 24xx),
  equity 3xxx (opening 31xx, retained_earnings 32xx, owner 33xx, fx_clearing 35xx),
  revenue 4xxx (commission 41xx, spread 42xx, fx_gain 43xx, office 45xx),
  expense 5xxx (exchange_fee, network, fx_loss 53xx, office_expense 55xx).
- **UI-канон уже частично**: `treasury_v2` — TreasuryShell + tabs: AssetsTab, LiabilitiesTab,
  EquityTab, DashboardTab, JournalTab, **PostingTab** (проводки Дт/Кт), **TurnoverTab (ОСВ)**,
  CashFlowTab, CorrespondentsTab, PnLTab, PaymentCalendarTab, DealsTab; OfficePicker, PeriodPicker,
  BalanceCheckBar; AccountsPage, ShareAccountsView.
- **Витрины сходятся с леджером**: `v_account_balances` перепойнтнут на `ledger.balances`
  (проверено), `ledger.balances` == `journal_entries` до копейки (проверено).
- Читатели: `ledgerReaders.js`, `cashierDealsReader.js`, `treasury/*selectors`.

**Что КОНФЛИКТУЕТ / чего не хватает (скоуп работ):**
1. **Единицы сумм.** Канон CP PAY = **bigint минорные единицы**. Касса = `journal_entries.amount`
   **numeric**. Это расхождение хранилища. Решение — вопрос владельцу (мигрировать в bigint-minor
   1-в-1 с каноном ИЛИ оставить numeric; `money.js` минорные единицы на фронте уже есть).
2. **Ключ идемпотентности** — сейчас из request_hash, канон = `{op}:{entity}:{request_id}`.
   Выровнять формат.
3. **RLS выключен на 9 таблицах `ledger.*`** (долг безопасности) — до боевого казначейства
   включить с политиками (иначе anon-ключ читает/пишет леджер).
4. **План счетов не полон под обмен**: нет явных **валютных ПОЗИЦИЙ платформы с формой**
   (Рубль нал / Доллар нал / Лира нал / USDT·TRC20 …) как строк канона С8. Есть fx_clearing 35xx,
   но не позиционная витрина «форма колонкой».
5. **Лоро под обмен** — есть customer_liab 21xx (глобальные) + партнёры, но не по-контрагентно
   как счета Лоро (оптовики/постоянные клиенты, кому должны/кто должен).
6. **5 операций обменника** как канонические RPC отсутствуют (внесение/выдача/обмен-через-позиции-
   с-rate_basis-и-маржой/перевод-между-своими/корректировка-по-инвентаризации).
7. **Операция «начальные остатки» с датой** (инвентаризация 7 касс) — нет.
8. **Курсовой канон С8/12** (база ЦБ + per-валюта источник + спред, две ручки, кросс-инвариант) —
   в кассе своя модель (`pairs`/`office_rate_overrides` + фиды rapira/tolunay/cbr). Механику надо
   свести к канону (две ручки/кросс-инвариант), но у кассы **свои клиентские курсы**.
9. **UI-дельты до канона**: единый `AccountRow` (№·имя·валюта-колонкой·форма-колонкой·остаток·
   $/€-эквиваленты, tabular-nums); страничная навигация без развёрток + крошки; банк-выписка
   (входящий сверху → running balance у строки → обороты → исходящий снизу → период); карточка
   транзакции Дт/Кт-парами; ОСВ+CSV; переходы по сторонам проводки в их счета. Часть уже есть
   (Turnover/Journal/Posting) — выровнять, не строить заново.
10. **Тестовые данные леджера** (41 tx / 108 проводок) — под снос перед стартом (чистые остатки).

**Что НЕ переносим** (подтверждено): QR/эквайринг/pmts, мерчанты/точки/POS, KYB, клиентские
кабинеты. Казначейство — операторами админки.

## (б) Схема БД — порт ядра + план счетов обмена

**Ядро — уже есть, доводим до канона:**
- Оставляем `ledger.accounts / transactions / journal_entries / balances / idempotency_keys`.
- Решение по единицам (вопрос владельцу): либо **миграция `amount`→bigint minor** (per-currency
  decimals из справочника валют) 1-в-1 с CP PAY, либо фиксируем numeric и документируем отступление.
- Ключ идемпотентности → `{op}:{entity}:{request_id}` (обёртка над текущим request_hash).
- Σ=0 per-currency, ≥2 проводки, immutable, reversal-каскад — **как есть** (канон соблюдён).
- RLS on + политики (`authenticated` read, service-role write) на все `ledger.*`.

**План счетов под обмен (расширение чартера):**
- **Ностро/кассы** — 7 физических касс × валюты (нал), банковские счета, крипто-кошельки
  (USDT/TRX по сетям TRC20/ERC20/BEP20). Базой берём существующие cash 111x + crypto 13xx,
  добиваем недостающие пары офис×валюта×форма.
- **Лоро** — по-контрагентные счета (оптовики/постоянные): тип liability/asset с client/partner-
  аналитикой (`client_dim_required`), создаются при первой операции с контрагентом (или вручную).
- **Капитал = валютные позиции платформы с формой** — новые счета-позиции per валюта+форма
  (Рубль нал, Доллар нал, Лира нал, USDT·TRC20, …); витрина С8: позиции строками, служебные
  (клиринг) внутри выписки позиции, **все валюты открытых счетов в балансе**.
- **Аналитические** — «Доход обмена» (маржа), «Расходы» (сеть/операц.) — есть 41xx/43xx/55xx,
  добавить «Доход обмена» как явный revenue-счёт, если канон требует отдельной строки.
- Нумерация — по канону coincash (сверить SQL эталона при написании кода).

**Обмен и Σ=0 через кросс-валюту:** т.к. Σ=0 per-currency, операция «обмен RUB→USDT» балансируется
**через позиции/клиринг** каждой валюты (нога RUB замыкается на позицию RUB, нога USDT — на позицию
USDT, маржа → «Доход обмена»), с фиксацией `rate_basis` в metadata (как в create_deal_v2 сейчас).

## (в) Маппинг существующих сущностей кассы → новая модель

| Сущность кассы (сейчас) | В модели казначейства |
|---|---|
| `offices` (7, uuid: Mark Antalya, Terra City, Istanbul, Liman, Москва Вася, International, St.pt) | Ностро/кассы — счета cash/bank/crypto per офис×валюта×форма |
| `participants` / partner_accounts (контрагенты) | Лоро (оптовики/постоянные) с client/partner-аналитикой |
| `deals`/`cashier_deals`/`ledger.transactions` (старые заявки, 41 tx тест) | **Леджер НЕ трогают.** Снос тестовых, старт с чистых остатков |
| `pairs`/`office_rate_overrides`/`external_rates`/`special_rates` + rapira/tolunay/cbr | Курсовой слой обмена: клиентские курсы + rate_basis в операции «обмен» |
| `users` (owner/admin/accountant/manager) | Операторы админки казначейства (роли — вопрос владельцу) |
| `money.js` минорные единицы | Совпадает с bigint-minor каноном (если мигрируем amount) |

**Старт с чистых остатков:** старые заявки/движения в новый леджер не мигрируем; казначейство
запускается **пустым** и наполняется операцией «начальные остатки» = **физическая инвентаризация
7 касс** (с датой, комментарием, audit). Без инвентаризации — леджер пустой.

## (г) Этапы

**Этап 1 — Ядро + Σ=0 (в основном есть → доводка).**
- Решение bigint-minor vs numeric + миграция (если да).
- Ключ идемпотентности `{op}:{entity}:{request_id}`.
- RLS on + политики на `ledger.*`.
- Снос тестовых 41 tx / 108 проводок (после PITR-бэкапа).
- Операция **«начальные остатки»** (дата, per-офис, комментарий, audit) → баланс из инвентаризации.
- Ворота: Σ=0 держит, balances==journal_entries, идемпотентность, тесты.

**Этап 2 — Счета + операции.**
- Достроить чартер: позиции-с-формой, Лоро по-контрагентно, недостающие Ностро/кассы.
- 5 канонических RPC: `deposit` (внесение), `withdraw` (выдача), `exchange` (валюта→валюта через
  позиции + rate_basis + маржа на «Доход обмена»), `transfer` (касса↔касса/банк, инкассация),
  `inventory_adjust` (корректировка по инвентаризации, обязательный комментарий + audit).
- Каждая — атомарная двойная запись, идемпотентна, через существующий постинг-мастер.

**Этап 3 — UI-канон.**
- Единый `AccountRow` (№·имя·валюта·форма·остаток·$/€, tabular-nums) — выровнять существующие
  Assets/Liabilities/Equity/Accounts.
- Дашборд Финансов → Лоро/Ностро/Капитал; страничная навигация (клиент→страница счетов→счёт→ОСВ)
  без развёрток + крошки; переходы по сторонам проводки.
- Банк-выписка (входящий→running balance→обороты→исходящий→период); карточка транзакции Дт/Кт-парами.

**Этап 4 — ОСВ + CSV.**
- Выровнять `TurnoverTab` под канон ОСВ (обороты/сальдо по счетам за период) + экспорт CSV.
- Курсовой слой: свести к «две ручки + кросс-инвариант» (С8/12), сохранив клиентские курсы кассы.
