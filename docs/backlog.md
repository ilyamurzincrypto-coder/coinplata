## Решить судьбу «International Office»

**Заведено:** 2026-08-27, при подготовке Экрана 4 «Счета · Крипто».
**Переформулировано:** 2026-08-27 по дельте эталона r6.
**Статус:** открыта, решение за владельцем. Из PR Экрана 4 убрана —
данные не трогаем, офис не активируем, кошелёк не перепривязываем.

**Что уже НЕ является проблемой UI.** Ревизия 6 эталона закрыла
презентационную часть: группы строятся по фактическому офису кошелька,
включая неактивные, и «International Office» показывается обычной группой
с оранжевой пометкой «офис неактивен · кошельки вне городов». Группа
«Без офиса» из макета убрана — она утверждала то, чего в данных нет.
Открытым остаётся только вопрос учёта: чем этот офис должен быть.

**Что на самом деле в данных** (`public.accounts`, прод, проверено SQL):

| поле | значение |
|---|---|
| id | `0fb6b363-dec9-47a4-89ff-c77b2ca3ca99` |
| name | WW-135 (kit out) |
| network / currency | TRC20 / USDT |
| address | `TYtC1HoczFTciw1Pp6c5m2vR6by8W1j9nd` |
| office_id | `63edef46-a114-4c98-9a38-497864ca1900` |
| aegis_wallet_id | `cmrx8r0ol0kok6mx5xdq8ndgn` |
| active | true |

То есть **`office_id` не пустой**. Формулировка «кошелёк не привязан» неточна:
он привязан к офису `63edef46…` = **«International Office» (city Worldwide)**,
у которого `active = false` и `coinpoint_office_code = null`. UI строит группы
по активным офисам, неактивный в список не попадает — и кошелёк проваливается
в «Без офиса».

**Вопрос владельцу:** чем должен быть «International Office» в учёте?

1. Легитимный контейнер для кошельков вне городов — тогда его стоит
   активировать (`active = true`) и, возможно, выдать
   `coinpoint_office_code`, чтобы он перестал быть исключением в других
   местах, где список офисов фильтруется по активным.
2. Технический артефакт — тогда WW-135 перепривязать к реальному офису,
   а сам офис оставить выключенным.

Влияет не только на ведомость: по активным офисам фильтруются и другие
экраны, поэтому выбор лучше сделать один раз и явно. Пока решения нет,
ведомость показывает офис как есть — это честно и ничего не искажает.

## Мобильные карточки счетов — перевести в табачный стиль

**Заведено:** 2026-08-27, при сдаче Экрана 4 (эталон r6).
**Статус:** открыта, долг по дизайну.

В PR Экрана 4 десктопная ведомость переведена на табачную палитру
(`surface-apps` + `apps-line*`), а мобильная ветка (`≤768`, `MobileRow` и
карточки офисов в `CryptoAccountsList`) осталась на прежних токенах
(`bg-surface`, `border-border`). Решение оставить её как есть было
сознательным — эталон r6 описывает десктоп, и трогать вслепую то, чего нет
в макете, дороже, чем зафиксировать долг.

**Что сделать:** привести мобильные карточки к тому же табачному набору,
когда появится мобильный кадр эталона (или по прямому решению, если
достаточно перенести палитру один в один).

## Срок жизни заявки — протухание/чистка с освобождением резерва

**Заведено:** 2026-08-27, по итогам живого просмотра секции «Заявки».
**Статус:** открыта. **Процессное решение за Ильёй — в PR не лезть.**

**Проблема.** Заявки в статусе `pending` живут вечно. На проде их 16, и
среди них есть висящие с 11 августа. Каждая держит резерв в «Остатках»:
по наблюдению владельца — порядка 1,4 млн TRY заморожено под заявки,
встречи по которым прошли две недели назад. Список будет только копить
трупы: сейчас в нём нет ни одного механизма, который убирает заявку без
ручного участия.

**Что уже сделано в UI (и чего недостаточно).** Просроченные не прячутся:
они гасятся до `#B4AB8D`, получают оранжевую подпись «прошла · N дней» и
намеренно остаются в дефолтной вкладке «Сегодня» — чтобы мозолить глаза.
Это лечит видимость, но не причину: резерв всё равно заморожен.

**Варианты (выбор владельца):**

1. **Авто-протухание.** У заявки появляется срок жизни (например, N суток
   после `meeting_at`), по истечении — статус `expired`, резерв
   освобождается. Нужен крон и решение, что делать с уже висящими.
2. **Ручная чистка.** Кассир закрывает заявку кнопкой «отменить» из
   карточки; UI подсвечивает кандидатов (просрочка > N дней). Дешевле,
   но зависит от дисциплины.
3. **Гибрид:** авто-протухание с уведомлением менеджеру за сутки.

Ключевой вопрос, без которого нельзя выбирать: **освобождение резерва —
это отмена заявки или отдельная операция?** От ответа зависит, трогает ли
это леджер (и тогда задача перестаёт быть мелкой).

## Табачный рескин плотных разделов (Казначейство, Контрагенты)

**Заведено:** 2026-08-27, при закрытии этапа 3 дизайн-миграции.
**Статус:** открыта. **Отдельный проект, стартует с новой ревизии эталона.**

Этап 3 привёл Казначейство, Контрагентов и Настройки к общей палитре,
радиусам и типографике (Onest + tnum), но **вёрстку и плотность не трогал,
а таблицы этих разделов НЕ переводил в табачный стиль** — сознательно:
эталон r6 описывает табачные таблицы только для «Заявок» (`.deals`) и
ведомости кошельков (`.wal`). Переносить их вид на плотные бухгалтерские
таблицы вслепую нельзя: у них другая плотность, больше колонок и другая
роль (работа с проводками, а не просмотр ленты).

**Что нужно для старта:** ревизия эталона с кадрами этих разделов —
как минимум оборотно-сальдовая ведомость, дерево счетов и список
контрагентов. Без них непонятно, что делать с плотностью строк,
группировками по классам счетов и колонкой сальдо.

**Токены готовы:** `surface-apps`, `apps-group`, `apps-line`,
`apps-line-v`, `apps-line-h`, `apps-muted`, `apps-warn` уже заведены и
обкатаны на двух разделах — новый проект начнёт не с нуля.

## ✅ Спред QR — из localStorage в rate_blocks.config

**Заведено:** 2026-08-27, по итогам инцидент-проверки (спред слетел с 8% на 1%).
**СДЕЛАНО:** 2026-09-01, `lib/qrSpread.js`. Источник — `rate_blocks.config`,
localStorage низведён до офлайн-кэша, молчаливый дефолт `1` убран совсем:
нет значения — панель говорит «спред не загружен» и НЕ считает курс.
Вопрос «читать таблицу фазы 1 раньше флага» снят архитектором: это настройка,
а не расчётный путь. **Осталось решить:** RLS `rate_blocks_update_admin`
пускает только owner/admin, поэтому шесть менеджеров потеряли возможность
править спред (раньше могли — в своём браузере). Сейчас поле у них
read-only с подписью. Если менеджер должен уметь — нужна правка политики.

**Проблема.** `QrRubPanel.jsx:12` читает спред из localStorage:

```js
export const QR_SPREAD_KEY = "qr_spread_pct_v1";
export const readQrSpread = () => {
  try { const v = localStorage.getItem(QR_SPREAD_KEY); return v == null ? "1" : v; }
  catch { return "1"; }
};
```

Это боевой параметр ценообразования, живущий в браузере одного человека.
Следствия, все три подтверждены на практике:

1. **Теряется от чистки браузера.** 27.08 Safari вычистил хранилище — вместе
   с сессией пропал и спред, панель молча взяла дефолт `1` вместо боевых `8`.
2. **Свой у каждого кассира.** У второго пользователя (Windows/Chrome) там
   своё значение — панели показывают разные курсы QR одновременно.
3. **Не переживает смену устройства** и не оставляет следа, кто менял.

**Что сделать.** Панель читает `spread_pct` из `rate_blocks.config` (место
фаза 1 уже завела: блок `qr`, `config = {"provider":"cbr","spread_pct":1}`),
запись — из редактора курсов, localStorage остаётся только кэшем для оффлайна.
Одно значение на всех + след в БД, кто и когда менял.

**Решение, которое надо принять явно (не молча):** правка формально заставит
фронт ЧИТАТЬ таблицу фазы 1 раньше фича-флага. Аргумент за: это настройка, а
не расчётный путь — курс по-прежнему считается старым кодом, из новой таблицы
берётся одно число. Аргумент против: «фаза 1 не видна нигде до флага» —
формулировка без исключений. Альтернатива, если решим не трогать фазу 1
раньше срока: держать спред строкой в существующей таблице настроек и
переехать в `rate_blocks` вместе с мостом.

**Согласовать с Ильёй до начала работы.**

**Временная мера (сделана в пассе 2 панели):** при чтении спреда с подстановкой
дефолта панель показывает янтарную пометку «спред хранится локально —
проверьте значение». Молчаливый дефолт на боевом параметре сегодня чуть не
стоил денег.

## Миграция хранилища сессии на cookie-storage

**Заведено:** 2026-08-31, в auth-PR (спиннер / проба / in-memory fallback).
**Статус:** открыта. **Только с планом миграции живых сессий.**

Auth-PR лечит симптом честно: если браузер не даёт писать в localStorage,
сессия живёт в памяти вкладки и человек об этом предупреждён. Но она всё
равно не переживает перезагрузку — а в Safari с его политикой хранилища это
происходит регулярно.

Радикальное лечение — держать сессию в cookie (`@supabase/ssr`-подобный
storage): cookie переживают чистку localStorage и работают в режимах, где
Safari режет site data.

**Почему не сделано сейчас:** смена хранилища разлогинивает всех, у кого
сессия лежит в localStorage — на момент записи это одиннадцать
пользователей. Нужен план: читать оба хранилища в переходный период,
писать в cookie, снять localStorage-чтение через N недель. Это отдельная
работа, а не строчка в конфиге.

**Гардрейл, который соблюдён в auth-PR:** `storageKey` и формат значения
не менялись — подменён только бэкенд хранения, поэтому живые сессии
переживают деплой.
