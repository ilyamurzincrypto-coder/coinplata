## Решить судьбу «International Office»

**Заведено:** 2026-08-27, при подготовке Экрана 4 «Счета · Крипто».
**Переформулировано:** 2026-08-27 по дельте эталона r6.
**Статус:** открыта, решение за владельцем. Из PR Экрана 4 убрана —
данные не трогаем, офис не активируем, кошелёк не перепривязываем.

**Что уже НЕ является проблемой UI.** Ревизия 6 эталона закрыла
презентационную часть: группы строятся по фактическому офису кошелька,
включая неактивные, и «International Office» показывается обычной группой
с оранжевой пометкой «офис неактивен · кошельки вне городов». Группа
«Без офиса» из макета убрана — она утверждала то, чего в данных нет.
Открытым остаётся только вопрос учёта: чем этот офис должен быть.

**Что на самом деле в данных** (`public.accounts`, прод, проверено SQL):

| поле | значение |
|---|---|
| id | `0fb6b363-dec9-47a4-89ff-c77b2ca3ca99` |
| name | WW-135 (kit out) |
| network / currency | TRC20 / USDT |
| address | `TYtC1HoczFTciw1Pp6c5m2vR6by8W1j9nd` |
| office_id | `63edef46-a114-4c98-9a38-497864ca1900` |
| aegis_wallet_id | `cmrx8r0ol0kok6mx5xdq8ndgn` |
| active | true |

То есть **`office_id` не пустой**. Формулировка «кошелёк не привязан» неточна:
он привязан к офису `63edef46…` = **«International Office» (city Worldwide)**,
у которого `active = false` и `coinpoint_office_code = null`. UI строит группы
по активным офисам, неактивный в список не попадает — и кошелёк проваливается
в «Без офиса».

**Вопрос владельцу:** чем должен быть «International Office» в учёте?

1. Легитимный контейнер для кошельков вне городов — тогда его стоит
   активировать (`active = true`) и, возможно, выдать
   `coinpoint_office_code`, чтобы он перестал быть исключением в других
   местах, где список офисов фильтруется по активным.
2. Технический артефакт — тогда WW-135 перепривязать к реальному офису,
   а сам офис оставить выключенным.

Влияет не только на ведомость: по активным офисам фильтруются и другие
экраны, поэтому выбор лучше сделать один раз и явно. Пока решения нет,
ведомость показывает офис как есть — это честно и ничего не искажает.

## Мобильные карточки счетов — перевести в табачный стиль

**Заведено:** 2026-08-27, при сдаче Экрана 4 (эталон r6).
**Статус:** открыта, долг по дизайну.

В PR Экрана 4 десктопная ведомость переведена на табачную палитру
(`surface-apps` + `apps-line*`), а мобильная ветка (`≤768`, `MobileRow` и
карточки офисов в `CryptoAccountsList`) осталась на прежних токенах
(`bg-surface`, `border-border`). Решение оставить её как есть было
сознательным — эталон r6 описывает десктоп, и трогать вслепую то, чего нет
в макете, дороже, чем зафиксировать долг.

**Что сделать:** привести мобильные карточки к тому же табачному набору,
когда появится мобильный кадр эталона (или по прямому решению, если
достаточно перенести палитру один в один).

## Срок жизни заявки — протухание/чистка с освобождением резерва

**Заведено:** 2026-08-27, по итогам живого просмотра секции «Заявки».
**Статус:** открыта. **Процессное решение за Ильёй — в PR не лезть.**

**Проблема.** Заявки в статусе `pending` живут вечно. На проде их 16, и
среди них есть висящие с 11 августа. Каждая держит резерв в «Остатках»:
по наблюдению владельца — порядка 1,4 млн TRY заморожено под заявки,
встречи по которым прошли две недели назад. Список будет только копить
трупы: сейчас в нём нет ни одного механизма, который убирает заявку без
ручного участия.

**Что уже сделано в UI (и чего недостаточно).** Просроченные не прячутся:
они гасятся до `#B4AB8D`, получают оранжевую подпись «прошла · N дней» и
намеренно остаются в дефолтной вкладке «Сегодня» — чтобы мозолить глаза.
Это лечит видимость, но не причину: резерв всё равно заморожен.

**Варианты (выбор владельца):**

1. **Авто-протухание.** У заявки появляется срок жизни (например, N суток
   после `meeting_at`), по истечении — статус `expired`, резерв
   освобождается. Нужен крон и решение, что делать с уже висящими.
2. **Ручная чистка.** Кассир закрывает заявку кнопкой «отменить» из
   карточки; UI подсвечивает кандидатов (просрочка > N дней). Дешевле,
   но зависит от дисциплины.
3. **Гибрид:** авто-протухание с уведомлением менеджеру за сутки.

Ключевой вопрос, без которого нельзя выбирать: **освобождение резерва —
это отмена заявки или отдельная операция?** От ответа зависит, трогает ли
это леджер (и тогда задача перестаёт быть мелкой).
